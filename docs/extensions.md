# Viewer extensions

An extension here is a small module in `src/web/extensions` that works against the `ViewerAdapter` interface (see [architecture.md](architecture.md)), plus an optional React panel in `src/web/panels`. Modules never touch the Autodesk Viewer globals directly, so they run on both the real and the mock adapter and can be tested without a browser viewer.

## Structure

- `src/web/extensions/<name>.ts`: pure logic. Takes an adapter or `PropertyRow[]` and returns data or performs an action.
- `src/web/extensions/index.ts`: re-exports each module.
- `src/web/panels/<Name>.tsx`: the UI. Gets the adapter from `useViewer()` (through `useResolvedAdapter`, which also accepts an `adapter` prop for tests) and reads properties with `usePropertyRows`.
- `src/web/panels/index.ts`: exports the panel. A pane entry in `src/web/layout/paneRegistry.ts` places it in the layout (see [layout.md](layout.md)).
- `src/web/extensions/extensions.test.ts` and `panels/panels.test.tsx`: unit tests.

Property rows have the shape `{ dbId, name, properties, modelId?, modelName? }`. `adapter.getLeafProperties(names)` returns one row per leaf element of every loaded model, with a value or `null` for each requested property name and the model it came from. In a combined view dbIds repeat across models, so never key data by `dbId` alone. Use `scopeRows(rows, scope)` from `viewer/modelScope.ts` to show one model or `ALL_MODELS`. Hidden models are not read. Summary and dashboard show an All models / one model switch (`ModelScope.tsx`, `useModelScope`) when the viewer holds two or more loaded models; All models counts the union, so values are summed across models. A model whose properties could not be read has `propertiesError` set; show `unavailableModels(adapter.getModels())` next to partial results.

## Existing extensions

**Viewer tools** (`tools/`). Every toolbar tool is a class that extends `ViewerTool` (`tools/kernel/ViewerTool.tsx`): `PaintTool`, `ExcelExportTool`, `GlbExportTool` and `IfcExportTool`. `tools/index.ts` registers them in toolbar order in the `TOOLS` registry. `ViewerPane` calls `useViewerTools(TOOLS, { adapter, active, suffix, fileName, report })` when its `tools` prop is true (the default). The hook reads each tool's own settings, asks every enabled tool to `contribute` its toolbar entries, merges them into the one `ToolGroupSpec` `bim-showcase-hub-tools` and registers it with `adapter.registerToolGroup`. It rebuilds the group only when a tool's `toolbarSignature` changes (by default its enabled flag, for paint also the palette and intensity), so editing export options never re-registers the toolbar, and it calls `onDisabled` when a tool goes from on to off (paint clears its colours). Export status reaches the viewer as a badge through `ctx.report`. On the real viewer the group becomes the Autodesk extension `BimShowcaseHub.Tools` in the native toolbar. On the mock viewer it is a toolbar group with a paint flyout. Find the buttons by their accessible names or titles: "Paint selection", the swatch labels, "Reset appearance", "Export to Excel" and "Export geometry (GLB)" and "Export IFC".

**Paint brushes** (`paintBrushes.ts`, `panels/PaintChip.tsx`, `tools/paint/`). `PAINT_PRESETS` defines red, green and blue and is the default palette. The Paint brushes settings window holds a global list of up to 8 hex swatches and an intensity (10 to 100 percent, default 50; it is theming intensity, not opacity). `paletteToPresets` turns them into the toolbar swatches, and `ViewerPane` re-registers the tool group when they change. Painted colour comes from the swatch hex, so the default red is `#ef4444` at 50 percent. `paintSelection` reads `adapter.getModelSelection()` (dbIds paired with their model), calls `setModelThemingColor` and clears the selection, so it paints across every model of a combined view. `resetPaint` calls `clearThemingColors`. The viewer tool group uses these functions. `PaintChip` is the small swatch used in the UI.

**Model summary** (`modelSummary.ts`, `panels/ModelSummaryPanel.tsx`, `panels/SummaryTable.tsx`). `summarize(rows, propertyNames)` counts values for each property (Assembly Code, Classification Code and Name by default), sorted by count and then by value. Empty values are labeled `(empty)`. The panel shows loading, empty and error states and a Refresh button. It is the Model summary pane; its collapsed state is part of the saved layout (`bsh.layout.v1`), and the count column does not wrap. The toolbar has a text filter, Copy table (tab-separated), Download CSV and Show all elements. The other settings live in the Summary settings modal (`panels/SummarySettings.tsx`, modal id `summary-settings`): hide `(empty)`, minimum count, sort by count or value, comfortable or compact density, column toggles, the row click action (select, isolate, or select and zoom) and a reset. Open it from the gear button in the panel header (the `onOpenSettings` prop) or from the Summary row of Settings (the Panes list), which opens the same window. `usePersistedState` broadcasts changes on `window`, so every instance of a key stays in sync. Per-property "% empty" badges show the QA signal. These view settings are stored in `localStorage` (`bsh.summary.view.v1`, `bsh.summary.action.v1`) for the summary pane, not per pane instance. Clicking a value calls the adapter methods `selectModelIds`, `isolateModelIds` and `fitToSelection` with `(modelId, dbId)` pairs found by `itemsWithValues` in `elementActions.ts`; with several models, isolate only touches models that have a match. "Show all elements" calls `isolateModelIds([])`.

**Excel export** (`excelExport.ts`). `exportToXlsx(adapter, options)` reads the properties Category, Name, Assembly Code, Classification Code and Level, builds one sheet per Category value (sheet names are sanitized to Excel's rules and made unique), and writes the file with `write-excel-file`, loaded on demand. It reports progress through `ExportStatus` (`reading`, `building`, `done`, `empty`, `error`). The viewer shows the status as a badge for four seconds, with row counts formatted with separators. The file is named after the model and version (`exportFileName`, for example `Snowdon-Towers-v3-properties.xlsx`), or `model-properties.xlsx` without a file name. Each viewer registers its tool group with ids suffixed by a short key of its URN (`modelKey`), so two open viewers never share control ids. When the rows come from more than one model, every sheet starts with a `Model` column holding the model name. The Excel export settings window chooses the format (`xlsx`, `csv` with a BOM, `json`, or copy as tab-separated text), the row scope (all, selected, or isolated elements; `isolated` uses the optional `adapter.getIsolated()`, which only the real viewer implements), an optional About sheet or JSON `about` block (model names, URNs, date, scope, row count), and a file name pattern with `{model}` and `{date}`. Text cells that start with `=`, `+`, `-`, `@`, tab or return get a leading apostrophe in CSV and copied text so names cannot run as formulas. XLSX cells are written as text and are not prefixed. Exports over 20000 rows ask for confirmation. Logic lives in `exportFormats.ts`.

**GLB export** (`glbExport.ts`, `viewer/viewerGeometry.ts`, `viewer/geometryTypes.ts`). `exportGeometryToGlb(adapter, options)` asks `adapter.getGeometryParts()` for `{ parts, skipped }` and writes a binary glTF 2.0 file in the browser. `buildGlb` writes one node and one mesh per element: parts with the same model and `dbId` share a node, each part is one primitive, and the node carries `extras: { dbId, model }` so the geometry can be joined to the property rows by `dbId`. Materials are shared by colour, positions go straight into one binary buffer (the viewer's Z-up world becomes glTF's Y-up, in meters), and parts with broken indices are skipped. `RealViewerAdapter` reads the fragment list of every visible, ready model (`vb`/`vbstride`/`ib` with draw-call `offsets`, `matrixWorld`, `getUnitScale()`, material colour). It refuses to export while a model is still loading, and counts fragments it could not read (not loaded, no geometry, no world matrix) in `skipped`. The status badge, shared with the Excel export (the latest export wins), lists missing models and the skipped count in the error variant. The file is named after the model (`Snowdon-Towers-v3-geometry.glb`). `MockViewerAdapter` returns a real triangle box so mock tests cover the writer. The MVP drops textures, UVs and normals, and a fragment that holds several elements gets no `dbId`; see [research/2026-11-17-svf-to-glb-export.md](research/2026-11-17-svf-to-glb-export.md).

**IFC export** (`ifcExport.ts`, `ifc/mapToIfc.ts`, `ifc/buildIfc.ts`, `ifc/stepWriter.ts`, `ifc/classTable.ts`, `ifc/globalId.ts`, `viewer/viewerSource.ts`). `exportToIfc(adapter, options)` asks `adapter.getIfcSource()` for the geometry and Revit properties of every visible, ready model, maps them with `mapToIfc` and streams an IFC4 STEP file with `buildIfc` in the browser. Each element becomes one product with an `IfcTriangulatedFaceSet`, one property set per Revit property group, and, only for elements that have a `Type Name`, a shared type object (for example `IfcWallType`). Coordinates are the viewer's world space with its global offset applied, in meters or millimeters (the length unit setting): they are not shared or survey coordinates, so a federation with a native Revit IFC will show an offset. The Category is read from the Other group first, where the reader puts the hidden `__category__` value. The element class comes from the Revit `Category` through `classTable.ts` (walls to `IfcWall`, doors to `IfcDoor` and so on, anything unknown to `IfcBuildingElementProxy`), and storeys are built from the `Level` property (elements without one go to the fallback storey). Each model becomes one `IfcBuilding`. A GlobalId is the compressed 22-character form of the Revit `externalId` (a GUID plus a hex element suffix, which is XORed into the last four bytes) when it has that shape, otherwise a stable hash of the model URN and the `externalId` or `dbId`; a duplicate id gets a hash of its own. Property sets, storeys, types and relationships get ids hashed from stable keys (element GlobalId, building GlobalId, names), so re-exports keep them. `viewerSource.ts` reads `externalId` from the bulk property items and falls back to `getExternalIdMapping`. It reads the Revit `Category` from the viewer's hidden `__category__` group (other `__` groups are skipped). The storey lookup tries the configured level property first, then `LEVEL_FALLBACKS` in `mapToIfc.ts` (`Level`, `Base Level`, `Reference Level`, `Schedule Level`). When an element has no plain `Level` but the viewer holds one as a dbId reference in the `__internalref__` group, `viewerSource.ts` bulk-reads the distinct referenced nodes, takes their name (a trailing ` [id]` is removed) and adds it as `Constraints.Level`; if the lookup fails the element is left as it was. Not exported: materials beyond a colour, openings, relationships between elements, quantities, and 2D sheets. The IFC export settings window sets class overrides, included or excluded property sets, the level property, the fallback storey and the project, site, building, author and organisation names. The result is a mesh-based coordination view, not a Revit IFC export, and Revit may not display `IfcTriangulatedFaceSet` geometry from IFC4 files, so open the file in a viewer such as BIMvision, Solibri or Blender with IfcOpenShell. `npm run e2e:ifc` validates the export on a real Revit sample; see [development.md](development.md).

**Dashboard** (`dashboardData.ts`, `panels/DashboardPanel.tsx`, `panels/ChartCanvas.tsx`). `shapeChartData(rows, property)` counts values, keeps the top 11 and merges the rest into "Other" when there are more than 12 categories. The panel only draws the charts (Chart.js) and has a Bar, Doughnut or Both switch; every other setting lives in the Dashboard settings modal (`panels/DashboardSettings.tsx`, modal id `dashboard-settings`), opened from the gear in the panel header (`onOpenSettings`) or from the Dashboard row of Settings (the Panes list), which opens the same window. It holds the preset, the group-by property, the maximum categories (3 to 30, default 12), the chart type and the chart click action, and is stored in `bsh.dashboard.view.v1`. Charts redraw with the theme colors when the theme changes. Series colors (`seriesColors`) come from an 8-color colour-blind-safe palette per theme (Okabe-Ito based, `CHART_PALETTES`); a value's color comes from a hash of its label, so it is the same in every chart, with the next free slot used when two values in one chart collide, a faded repeat after 8 values, and a neutral grey for "Other". The legend and the PNG use the same colors. Paint swatches are separate and unchanged. Each chart has PNG (drawn on the card surface color), CSV and Copy (tab-separated) buttons (`chartExport.ts`). Clicking a bar or slice runs the Chart click action (select, isolate, or select and zoom, stored in `bsh.dashboard.action.v1`; both keys are cleared on sign-out) on the elements of that bucket; the "Other" bucket covers all merged values. Presets (`dashboardPresets.ts`: Model health, By discipline, Quantities by type, Classification coverage) show one bar chart per property the model actually has and hide the rest; Single chart returns to the group-by property. Presets are built in and read-only; saving your own is not built. Presets assume Revit property names such as Discipline, Family and Type Name. It is the Dashboard pane; its collapsed state is part of the saved layout (`bsh.layout.v1`).

## Commands and the palette

Ctrl/Cmd+K opens the command palette (`src/web/commands`, design in `superpowers/specs/2026-11-18-command-palette-design.md`). `COMMANDS.register(source, () => Command[], priority?)` adds a source of commands; providers run each time the palette opens, so titles and `disabled` reasons are current. A command has `id`, `title`, `group`, optional `keywords`, `icon` and `disabled` (a reason string), and `run(host)`; `host.openModal(id)` opens a settings window. When two sources give the same id the higher priority wins, which is how the active viewer's live commands replace the shell's disabled placeholders. Existing sources: `AppCommands` (theme, settings windows, sign-out, tool commands, placeholders), `LayoutCommands` (panes, lock, reset, present) and each viewer through `useViewerTools` (export and element actions while its adapter is the active one). A tool adds commands by overriding `ViewerTool.commands(ctx, settings)`; the default gives its settings window and, when the tool sets `exportTitle`, one command per toolbar export. Recents (last 5 ids) are stored under `bsh.commands.recent.v1` and cleared on sign-out.

## Settings and modals

- Add a modal: write a `ModalDefinition` and add one line for it in `src/web/modal/registry.ts`. The registry already adds one modal per registered tool.
- App settings (`src/web/settings`, key `bsh-settings-v1`) hold only app-level fields: `sessionWarnMinutes` and `recentsLength`. The Settings modal shows those, the theme switch and a list of entry points that open each tool's and each pane's own window. It does not know any tool's fields.
- Each tool owns its settings: a `PersistedSetting` (storage key, defaults, sanitizer) with an `enabled` flag, saved under its own key (`bsh.tool.paint.v1`, `bsh.tool.excel.v1`, `bsh.tool.glb.v1`, `bsh.tool.ifc.v1`), and its own window (modal id `tool-<id>-settings`, title `<Tool title> settings`). The on/off switch is the first control of that window (`ToolSettingsFrame`). The Summary and Dashboard panes follow the same rule through `settings/paneSettings.ts`, which uses the same `PersistedSetting` primitive and `usePersistedSetting` hook as the tools.
- Sign-out (`forgetPersonal`) clears the personal keys and runs the registry's `scrubPersonal`, which calls each tool's `scrub`: the IFC tool blanks `author` and `organisation` and keeps every other value.
- Sign-out also rewrites the app blob down to `sessionWarnMinutes` and `recentsLength` (`scrubAppSettings`), so stray fields from older versions do not outlive the session.
- Tool group controls: `ToolGroupSpec.paint` may be omitted and `ToolGroupSpec.exports` is a list (Excel, GLB and IFC entries, each with `id`, `icon`, `tooltip` and `onExport`) that holds only the enabled tools' entries. The spec has one paint slot, so if two tools contribute paint the first registered wins.

## Add a tool

1. Write the logic in `src/web/extensions/<name>.ts` (see below), plus any settings type and sanitizer it needs next to it.
2. Add `src/web/tools/<id>/<Name>Tool.tsx`: a class that extends `ViewerTool<YourSettings>` and sets `id`, `title`, `description` and `settings` (`persistedSetting(key, defaults, sanitize)` with `enabled: readEnabled(raw)`), implements `contribute(ctx, settings)` and, for options, overrides `renderFields()` with a settings component built on `usePersistedSetting`. Use `exportEntry`, `exportFileName`, `confirmLargeExport` and `statusReporter` from `tools/kernel/exportKit.ts` for exports (the entry takes a task `label`, runs the work with a `{ task, signal }` job and reports progress, outcome and cancel through the task center), and read settings at click time with `ctx.current(this)`. Override `toolbarSignature`, `onDisabled` and `scrub` only when needed.
3. Register it in `src/web/tools/index.ts` (`.register(new YourTool())`). Nothing in app settings, `SettingsModal` or `ViewerPane` changes.
4. Test the class with a fake `ToolContext` (see `tools/glb/GlbExportTool.test.tsx`) and its window with `render(tool.renderSettings())`.

## Add an extension

1. Write the logic in `src/web/extensions/<name>.ts`. Accept a `ViewerAdapter` or `PropertyRow[]`. If it needs a viewer capability that the interface lacks, add the method to `ViewerAdapter`, implement it in both `RealViewerAdapter` and `MockViewerAdapter`, and extend `adapter.contract.test.ts`.
2. Export it from `src/web/extensions/index.ts`.
3. For viewer toolbar controls, add a `ViewerTool` (see Add a tool), extend `ToolGroupSpec` only for a new kind of control, then implement the new control in both the Autodesk extension (`viewer/autodeskTools.ts`) and `MockViewerAdapter.buildToolGroup`. Registration goes through `adapter.registerToolGroup(spec)`, which returns a disposer to call on cleanup.
4. For a panel, create `src/web/panels/<Name>.tsx` using `useResolvedAdapter` and `usePropertyRows`, use `StateBlock` for loading, empty and error states, and export it from `panels/index.ts`.
5. Add a pane for the panel to `PANES` in `src/web/layout/paneRegistry.ts` (see [layout.md](layout.md)).
6. Add tests with the mock adapter: logic in `extensions.test.ts`, UI in `panels.test.tsx`.
7. Run `npm run lint`, `npm run typecheck` and `npm test`, then check the page with `npm run dev:mock`.
