# Viewer extensions

An extension here is a small module in `src/web/extensions` that works against the `ViewerAdapter` interface (see [architecture.md](architecture.md)), plus an optional React panel in `src/web/panels`. Modules never touch the Autodesk Viewer globals directly, so they run on both the real and the mock adapter and can be tested without a browser viewer.

## Structure

- `src/web/extensions/<name>.ts`: pure logic. Takes an adapter or `PropertyRow[]` and returns data or performs an action.
- `src/web/extensions/index.ts`: re-exports each module.
- `src/web/panels/<Name>.tsx`: the UI. Gets the adapter from `useViewer()` (through `useResolvedAdapter`, which also accepts an `adapter` prop for tests) and reads properties with `useScopedRows`.
- `src/web/panels/index.ts`: exports the panel. A pane entry in `src/web/layout/paneRegistry.ts` places it in the layout (see [layout.md](layout.md)).
- `src/web/extensions/extensions.test.ts` and `panels/panels.test.tsx`: unit tests.

Property rows have the shape `{ dbId, name, properties, modelId?, modelName? }`. `adapter.getLeafProperties(names)` returns one row per leaf element of every loaded model, with a value or `null` for each requested property name and the model it came from. In a combined view dbIds repeat across models, so never key data by `dbId` alone. Use `scopeRows(rows, scope)` from `viewer/modelScope.ts` to show one model or `ALL_MODELS`. Hidden models are not read. Summary and dashboard show an All models / one model switch (`ModelScope.tsx`, the `models` control of `useScopedRows`) when the viewer holds two or more loaded models; All models counts the union, so values are summed across models. A model whose properties could not be read has `propertiesError` set; show `unavailableModels(adapter.getModels())` next to partial results.

## Existing extensions

**Viewer tools** (`tools/`). Every toolbar tool is a class that extends `ViewerTool` (`tools/kernel/ViewerTool.tsx`): `PaintTool`, `ExcelExportTool`, `GlbExportTool` and `IfcExportTool`. `tools/index.ts` registers them in toolbar order in the `TOOLS` registry (`ToolRegistry`). `ViewerPane` calls `useViewerTools(TOOLS, { adapter, active, suffix, fileName })` when its `tools` prop is true (the default). The hook reads each tool's own settings, asks every enabled tool to `contribute` its toolbar entries, merges them into the one `ToolGroupSpec` `bim-showcase-hub-tools` and registers it with `adapter.registerToolGroup`. It rebuilds the group only when a tool's `toolbarSignature` changes (by default its enabled flag, for paint also the palette and intensity), so editing export options never re-registers the toolbar, and it calls `onDisabled` when a tool goes from on to off (paint clears its colours). Exports report through the Task Center (see Tasks below), not through the viewer. On the real viewer the group becomes the Autodesk extension `BimShowcaseHub.Tools` in the native toolbar. On the mock viewer it is a toolbar group with a paint flyout. Find the buttons by their accessible names or titles: "Paint selection", the swatch labels, "Reset appearance", "Export to Excel" and "Export geometry (GLB)" and "Export IFC".

**Paint brushes** (`paintBrushes.ts`, `panels/PaintChip.tsx`, `tools/paint/`). `PAINT_PRESETS` defines red, green and blue and is the default palette. The Paint brushes settings window holds a global list of up to 8 hex swatches and an intensity (10 to 100 percent, default 50; it is theming intensity, not opacity). `paletteToPresets` turns them into the toolbar swatches, and `ViewerPane` re-registers the tool group when they change. Painted colour comes from the swatch hex, so the default red is `#ef4444` at 50 percent. `paintSelection` reads `adapter.getModelSelection()` (dbIds paired with their model), calls `setModelThemingColor` and clears the selection, so it paints across every model of a combined view. `resetPaint` calls `clearThemingColors`. The viewer tool group uses these functions. `PaintChip` is the small swatch used in the UI.

**Model summary** (`modelSummary.ts`, `panels/ModelSummaryPanel.tsx`, `panels/SummaryTable.tsx`). `summarize(rows, propertyNames)` counts values for each property (Assembly Code, Classification Code and Name by default), sorted by count and then by value. Empty values are labeled `(empty)`. The panel shows loading, empty and error states and a Refresh button. It is the Model summary pane; its collapsed state is part of the saved layout (`bsh.layout.v2`), and the count column does not wrap. The toolbar has a text filter, Copy table (tab-separated), Download CSV and Show all elements. The other settings live in the Summary settings modal (`panels/SummarySettings.tsx`, modal id `summary-settings`): hide `(empty)`, minimum count, sort by count or value, comfortable or compact density, column toggles, the row click action (select, isolate, hide, or select and zoom) and a reset. Open it from the gear button in the panel header (the `onOpenSettings` prop) or from the Summary row of Settings (the Panes list), which opens the same window. `usePersisted` (see Persisted records below) keeps every hook on a key in sync. Per-property "% empty" badges show the QA signal. The Summary pane keeps its view settings in `localStorage` (`bsh.summary.view.v1`, `bsh.summary.action.v1`, `bsh.summary.properties.v1`, `bsh.summary.scope.v1`). A summary pane you add (Panes menu, New model summary) has its own spec under `bsh.pane.modelSummary.<n>.v1` (model, element scope, properties, view and row click action) and the settings window opened from it edits that spec, with Reset view resetting only the view and action it edits. A new pane copies the main Summary's current view and action; a spec saved before view and action existed loads with the defaults. Only the main Summary uses the global keys. Clicking a value calls the adapter methods `selectModelIds`, `isolateModelIds`, `hideModelIds` and `fitToView` with `(modelId, dbId)` pairs found by `itemsWithValues` in `elementActions.ts`; with several models, isolate only touches models that have a match. "Show all elements" calls `showAll()`.

**Excel export** (`excelExport.ts`). `exportToXlsx(adapter, options)` reads the properties Category, Name, Assembly Code, Classification Code and Level, builds one sheet per Category value (sheet names are sanitized to Excel's rules and made unique), and writes the file with `write-excel-file`, loaded on demand. It reports progress through `ExportStatus` (`reading`, `building`, `done`, `empty`, `cancelled`, `error`), which the tool turns into a Task Center entry with Cancel; row counts are formatted with separators. The file is named after the model and version (`exportStem` and `exportFileName` from `tools/kernel/exportKit.ts`, for example `Snowdon-Towers-v3-properties.xlsx`), or `model-properties.xlsx` without a file name. Each viewer registers its tool group with ids suffixed by a short key of its URN (`modelKey`), so two open viewers never share control ids. When the rows come from more than one model, every sheet starts with a `Model` column holding the model name. The Excel export settings window chooses the format (`xlsx`, `csv` with a BOM, `json`, or copy as tab-separated text), the row scope (all, selected, visible or isolated elements, or a saved selection set; `isolated` uses the optional `adapter.getIsolated()`, which only the real viewer implements), the model scope, a "Rows to export" line with the live count and the Selection sets section (`panels/SelectionSets.tsx`). The count (`viewer/scopeCount.ts`) comes only from the shared row cache (`peekLeafRows`), so it never starts a read: it shows "counting…" and re-checks every second until a model's rows are cached, then equals the rows the export would write (the same `applyScope`, which the large-export confirm also sees). A set scope whose set was deleted falls back to all elements: the select shows "Deleted set (using all elements)" and the export ends as "Done with warnings" saying the set no longer exists, an optional About sheet or JSON `about` block (model names, URNs, date, scope, row count), and a file name pattern with `{model}` and `{date}`. Text cells that start with `=`, `+`, `-`, `@`, tab or return get a leading apostrophe in CSV and copied text so names cannot run as formulas. XLSX cells are written as text and are not prefixed. Exports over 20,000 rows ask for confirmation with a browser dialog (`confirmLargeExport`; e2e scripts must accept dialogs). Logic lives in `exportFormats.ts`.

**GLB export** (`glbExport.ts`, `viewer/viewerGeometry.ts`, `viewer/geometryTypes.ts`). `exportGeometryToGlb(adapter, options)` asks `adapter.getGeometryParts()` for `{ parts, skipped }` and writes a binary glTF 2.0 file in the browser. `buildGlb` writes one node and one mesh per element: parts with the same model and `dbId` share a node, each part is one primitive, and the node carries `extras: { dbId, model }` so the geometry can be joined to the property rows by `dbId`. Materials are shared by colour, positions go straight into one binary buffer (the viewer's Z-up world becomes glTF's Y-up, in meters), and parts with broken indices are skipped. `RealViewerAdapter` reads the fragment list of every visible, ready model (`vb`/`vbstride`/`ib` with draw-call `offsets`, `matrixWorld`, `getUnitScale()`, material colour). It refuses to export while a model is still loading, and counts fragments it could not read (not loaded, no geometry, no world matrix) in `skipped`. The task detail lists missing models and the skipped count, and the task ends as "Done with warnings" when anything was skipped or missing. The file is capped at 256 MB (`MAX_GLB_BYTES`): a larger model fails with "the file would be larger than 256 MB" before anything is written. The file is named after the model (`Snowdon-Towers-v3-geometry.glb`). `MockViewerAdapter` returns a real triangle box so mock tests cover the writer. The MVP drops textures, UVs and normals, and a fragment that holds several elements gets no `dbId`; see [research/2026-11-17-svf-to-glb-export.md](research/2026-11-17-svf-to-glb-export.md).

**IFC export** (`ifcExport.ts`, `ifc/mapToIfc.ts`, `ifc/buildIfc.ts`, `ifc/stepWriter.ts`, `ifc/classTable.ts`, `ifc/globalId.ts`, `viewer/viewerSource.ts`). `exportToIfc(adapter, options)` asks `adapter.getIfcSource()` for the geometry and Revit properties of every visible, ready model, maps them with `mapToIfc` and streams an IFC4 STEP file with `buildIfc` in the browser. Each element becomes one product with an `IfcTriangulatedFaceSet`, one property set per Revit property group, and, only for elements that have a `Type Name`, a shared type object (for example `IfcWallType`). Coordinates are the viewer's world space with its global offset applied, in meters or millimeters (the length unit setting): they are not shared or survey coordinates, so a federation with a native Revit IFC will show an offset. The Category is read from the Other group first, where the reader puts the hidden `__category__` value. The element class comes from the Revit `Category` through `classTable.ts` (walls to `IfcWall`, doors to `IfcDoor` and so on, anything unknown to `IfcBuildingElementProxy`), and storeys are built from the `Level` property (elements without one go to the fallback storey). Each model becomes one `IfcBuilding`. A GlobalId is the compressed 22-character form of the Revit `externalId` (a GUID plus a hex element suffix, which is XORed into the last four bytes) when it has that shape, otherwise a stable hash of the model URN and the `externalId` or `dbId`; a duplicate id gets a hash of its own. Property sets, storeys, types and relationships get ids hashed from stable keys (element GlobalId, building GlobalId, names), so re-exports keep them. `viewerSource.ts` reads `externalId` from the bulk property items and falls back to `getExternalIdMapping`. It reads the Revit `Category` from the viewer's hidden `__category__` group (other `__` groups are skipped). The storey lookup tries the configured level property first, then `LEVEL_FALLBACKS` in `mapToIfc.ts` (`Level`, `Base Level`, `Reference Level`, `Schedule Level`). When an element has no plain `Level` but the viewer holds one as a dbId reference in the `__internalref__` group, `viewerSource.ts` bulk-reads the distinct referenced nodes, takes their name (a trailing ` [id]` is removed) and adds it as `Constraints.Level`; if the lookup fails the element is left as it was. Not exported: materials beyond a colour, openings, relationships between elements, quantities, and 2D sheets. The IFC export settings window sets class overrides, included or excluded property sets, the level property, the fallback storey and the project, site, building, author and organisation names. The result is a mesh-based coordination view, not a Revit IFC export, and Revit may not display `IfcTriangulatedFaceSet` geometry from IFC4 files, so open the file in a viewer such as BIMvision, Solibri or Blender with IfcOpenShell. `npm run e2e:ifc` validates the export on a real Revit sample; see [development.md](development.md).

**Properties** (`panels/PropertiesPanel.tsx`, `panels/propertiesView.ts`). A user pane family (`properties:N`, Panes menu `New properties` or the palette) and the minimal read-only slice of the properties inspector: no editing, pinning or comparison. It shows the property list of the elements selected in the viewer, for one model: its spec `{ scope }` (model id, seeded with the active model, `bsh.pane.properties.<n>.v1`) is changed with the model select shown when two or more models are ready. It follows `adapter.onSelectionChange` and reads each selected element (the first 20) with the adapter method `getElementProperties({ modelId, dbId })`, which returns `{ dbId, name, properties: [{ category, name, value }] }` or `null`: the real adapter calls `model.getBulkProperties([dbId], {})` (no `propFilter`, so every non-hidden property comes back with its `displayCategory`; blank categories become "Other"), the mock adapter returns fixture values. Properties are grouped by category, filtered by a text box over category, name and value, and each row has a Copy button. States: "No model loaded", "Select an element", loading, error and "No matching properties".

**Dashboard** (`dashboardData.ts`, `panels/DashboardPanel.tsx`, `panels/ChartCanvas.tsx`). `shapeChartData(rows, property)` counts values, keeps the top 11 and merges the rest into "Other" when there are more than 12 categories. The panel only draws the charts (Chart.js) and has a Bar, Doughnut or Both switch; every other setting lives in the Dashboard settings modal (`panels/DashboardSettings.tsx`, modal id `dashboard-settings`), opened from the gear in the panel header (`onOpenSettings`) or from the Dashboard row of Settings (the Panes list), which opens the same window. It holds the preset, the group-by property, the maximum categories (3 to 30, default 12), the chart type and the chart click action. The Dashboard pane stores its view in `bsh.dashboard.view.v1`; each chart pane you add (Panes menu, New chart) is a `DashboardPanel` with its own view under `bsh.pane.chart.<n>.v1` and its own group-by, chart type and scopes in the pane header. Charts redraw with the theme colors when the theme changes. Series colors (`seriesColors`) come from an 8-color colour-blind-safe palette per theme (Okabe-Ito based, `CHART_PALETTES`); a value's color comes from a hash of its label, so it is the same in every chart, with the next free slot used when two values in one chart collide, a faded repeat after 8 values, and a neutral grey for "Other". The legend and the PNG use the same colors. Paint swatches are separate and unchanged. Each chart has PNG (drawn on the card surface color), CSV and Copy (tab-separated) buttons (`chartExport.ts`). Clicking a bar or slice runs the Chart click action (select, isolate, hide, or select and zoom, stored in `bsh.dashboard.action.v1`; all dashboard keys are cleared on sign-out) on the elements of that bucket; the "Other" bucket covers all merged values. Presets (`dashboardPresets.ts`: Model health, By discipline, Quantities by type, Classification coverage) show one bar chart per property the model actually has and hide the rest; Single chart returns to the group-by property. The built-in presets are read-only. My presets (`panels/DashboardUserPresets.tsx`, in the Dashboard settings window) saves the current view under a name as a saved item of kind `dashboard-preset`; you can rename, apply and delete them, and Settings exports and imports them (see Saved items below). Presets assume Revit property names such as Discipline, Family and Type Name. It is the Dashboard pane; its collapsed state is part of the saved layout (`bsh.layout.v2`).

## Commands and the palette

Ctrl/Cmd+K opens the command palette (`src/web/commands`, design in `superpowers/specs/2026-11-18-command-palette-design.md`). `COMMANDS.register(source, () => Command[], priority?)` adds a source of commands; providers run each time the palette opens, so titles and `disabled` reasons are current. A command has `id`, `title`, `group`, optional `keywords`, `icon` and `disabled` (a reason string), and `run(host)`; `host.openModal(id)` opens a settings window. When two sources give the same id the higher priority wins, which is how the active viewer's live commands replace the shell's disabled placeholders. Existing sources: `AppCommands` (theme, settings windows, sign-out, tool commands, placeholders), `LayoutCommands` (panes, lock, reset, present) and each viewer through `useViewerTools` (export and element actions while its adapter is the active one). A tool adds commands by overriding `ViewerTool.commands(ctx, settings)`; the default gives its settings window and, when the tool sets `exportTitle`, one command per toolbar export. Recents (last 5 ids) are stored under `bsh.commands.recent.v1` and cleared on sign-out.

## Settings and modals

- Add a modal: write a `ModalDefinition` and add one line for it in `src/web/modal/registry.ts`. The registry already adds one modal per registered tool.
- App settings (`src/web/settings/settings.ts`, key `bsh-settings-v1`) hold only app-level fields: `sessionWarnMinutes` and `recentsLength`. The Settings modal shows those, the theme switch, a list of entry points that open each tool's and each pane's own window, and the saved items import and export. It does not know any tool's fields. The old all-in-one settings migration is gone: other fields in a stored blob are ignored, and sign-out trims a valid object to the two app fields and removes a blob that is not a JSON object (truncated JSON, a number, a string, an array) (`scrubAppSettings`).
- Each tool owns its settings: a `PersistedRecord` (`defineRecord`, with storage key, defaults and a sanitizer) that includes an `enabled` flag, saved under its own key (`bsh.tool.paint.v1`, `bsh.tool.excel.v1`, `bsh.tool.glb.v1`, `bsh.tool.ifc.v1`), and its own window (modal id `tool-<id>-settings`, title `<Tool title> settings`). The on/off switch is the first control of that window (`ToolSettingsFrame`). The Summary and Dashboard panes follow the same rule through `settings/paneSettings.ts` (`PANE_SETTINGS`, records read with `usePaneSetting`, which is `usePersisted`), and the per-instance specs live in `layout/instanceSettings.ts`.
- Generated form: `components/SettingsForm.tsx` renders a `FormDefinition` (`title`, `intro`, `fields`, optional `reset`) over a value and an `onChange(patch)`. Field kinds are `toggle`, `number` (optionally a slider), `select`, `text`, `multi` (checkbox group) and `list` (text or colour items with add and remove). A tool sets `form` instead of overriding `renderFields()` and the kernel wraps it with `ToolForm`. The Paint tool (`PAINT_FORM`) and the Summary settings use it; the Excel and IFC windows have hand-written fields.
- Sign-out (`forgetPersonal`) clears the personal keys, including every `bsh.pane.` key, and runs the hooks registered in `tools/index.ts`: the registry's `scrubPersonal` calls each tool's `scrub` (the IFC tool blanks `author` and `organisation`, the Excel tool resets its model scope to all, other values stay), then `scrubAppSettings` runs. The tool settings keys are preferences, so they survive sign-out apart from that scrub.
- Tool group controls: `ToolGroupSpec.paint` may be omitted and `ToolGroupSpec.exports` is a list (Excel, GLB and IFC entries, each with `id`, `icon`, `tooltip` and `onExport`) that holds only the enabled tools' entries. The spec has one paint slot, so if two tools contribute paint the first registered wins.

## Persisted records

All browser storage goes through `src/web/storage.ts`; do not call `localStorage` directly.

- `defineRecord({ key, initial, sanitize, area?, codec? })` makes one record. `read()` always runs `sanitize`, so a corrupt or old value cannot reach a component. `area` is `'local'` (default) or `'session'`.
- `usePersisted(record)` returns `[value, update, reset]`; `update` takes a value or an updater.
- Key sets: add a key to `BSH_KEYS.personal` when it describes the user's models, layout or work (cleared on sign-out) and to `BSH_KEYS.preference` when it is a taste setting (kept). A family of keys is a prefix: `defineRecordFamily({ prefix, keyOf, initial, sanitize })` throws unless the prefix is in `BSH_PERSONAL_PREFIXES`, and `forget(arg)` removes one member. `bsh.pane.` is the only prefix today.
- The forget path: `forgetPersonal()` removes personal keys from both storage areas, clears the family caches, runs `onForgetPersonal` hooks and fires `bsh:forget`. A tool that keeps personal text in a preference-class record blanks it in `scrub`.
- Tests: `setStorageAdapter(memoryAdapter())` (from `storageAdapter.ts`) swaps the browser for an in-memory adapter and returns the previous one to restore; `persistedRecord.test.tsx` shows the pattern. Component tests that only need a working `localStorage` use `installMemoryStorage()` from `test/mockApi.ts`.

## Scoped rows

Read property rows through `useScopedRows(adapter, { names, elements, models })` in a panel and `readScopedRows(adapter, { names, scope })` in async code, never `readLeafRows` directly. They apply the model scope and the element scope (`all`, `selected`, `visible`, `isolated` or `set:<id>`, a saved selection set; a missing set falls back to `all` and the result carries `scopeNote`), share one per-adapter cache that only grows as callers ask for more property names, and report loading, progress, cancel and per-model failures. Panels render the result with `StateBlock`. See [architecture.md](architecture.md#scoped-rows).

## Tasks

Wrap work the user waits for in `startTask({ label, cancel?, retry? })` (`src/web/tasks/taskStore.ts`) and settle it with `finish`, `warn` (renders as "Done with warnings"), `fail` or `cancel`. `progress(fraction | null, detail)` updates a running task. The Task Center in the top bar lists tasks newest first with a state word, the detail, a progress bar while running, Cancel for running tasks that supplied `cancel`, Retry for failed tasks that supplied `retry`, and Dismiss. Model loads (`ViewerPane`) and exports report this way. For an export use `exportEntry`, which wraps `runOnce` and a `statusReporter(task, describe)` that turns `done`, `empty`, `error` and `cancelled` phases into task states. See [architecture.md](architecture.md#tasks).

## Saved items

`src/web/store` keeps named, user-made items in one record (`bsh.saved.v1`, personal). An item is `{ id, kind, name, version, updatedAt, data }`; `kind` is a lowercase tag (today `dashboard-preset` and `selection-set`). Use `readSaved(kind)`, `upsertSaved(item)` and `removeSaved(id)`; the store sanitizes names and data and refuses items that are too big. Settings, Saved items has Export (a `bsh-saved.json` file) and Import (merge by id, the newer `updatedAt` wins, invalid items are counted and skipped). A new kind needs only a `kind` string and its own sanitizer when read back. A selection set (`viewer/selectionSets.ts`) keeps `data.models`, a map from model id (URN) to captured dbIds, up to 10,000 elements; `saveSelectionSet`, `renameSet`, `deleteSet`, `selectSet` (through `selectModelIds`) and the `useSelectionSets` hook manage them. The palette has `Save selection as set` and one `Select set <name>` per set. Sets are personal, so sign-out removes them, and the Excel tool scrub resets a `set:` scope to all with the model scope.

## Add a tool

1. Write the logic in `src/web/extensions/<name>.ts` (see below), plus any settings type and sanitizer it needs next to it.
2. Add `src/web/tools/<id>/<Name>Tool.tsx`: a class that extends `ViewerTool<YourSettings>` and sets `id`, `title`, `description` and `settings` (`defineRecord` with `enabled: readEnabled(raw)` in the sanitizer, under a `bsh.tool.<id>.v1` key), implements `contribute(ctx, settings)` and, for options, sets `form` (a `FormDefinition`) or overrides `renderFields()` with a component built on `usePersisted`. Use `exportEntry`, `exportStem`, `exportFileName`, `confirmLargeExport` and `statusReporter` from `tools/kernel/exportKit.ts` for exports (the entry takes a task `label`, runs the work with a `{ task, signal }` job and reports progress, outcome and cancel through the Task Center), and read settings at click time with `ctx.current(this)`. Set `exportTitle` to get a palette export command. Override `toolbarSignature`, `onDisabled` and `scrub` only when needed.
3. Register it in `src/web/tools/index.ts` (`.register(new YourTool())`). The registry rejects a duplicate id or settings key. Nothing in app settings, `SettingsModal` or `ViewerPane` changes.
4. Test the class with a fake `ToolContext` (see `tools/glb/GlbExportTool.test.tsx`) and its window with `render(tool.renderSettings())`. `tools/kernel/kernel.test.tsx` covers the registry and the hook.

## Add an extension

1. Write the logic in `src/web/extensions/<name>.ts`. Accept a `ViewerAdapter` or `PropertyRow[]`. If it needs a viewer capability that the interface lacks, add the method to `ViewerAdapter`, implement it in both `RealViewerAdapter` and `MockViewerAdapter`, and extend `adapter.contract.test.ts`.
2. Export it from `src/web/extensions/index.ts`.
3. For viewer toolbar controls, add a `ViewerTool` (see Add a tool), extend `ToolGroupSpec` only for a new kind of control, then implement the new control in both the Autodesk extension (`viewer/autodeskTools.ts`) and `MockViewerAdapter.buildToolGroup`. Registration goes through `adapter.registerToolGroup(spec)`, which returns a disposer to call on cleanup.
4. For a panel, create `src/web/panels/<Name>.tsx` using `useResolvedAdapter` and `useScopedRows`, use `StateBlock` for loading, empty and error states, and export it from `panels/index.ts`.
5. Add a pane for the panel to `PANES` in `src/web/layout/paneRegistry.ts` (see [layout.md](layout.md)).
6. Add tests with the mock adapter: logic in `extensions.test.ts`, UI in `panels.test.tsx`.
7. Run `npm run lint`, `npm run typecheck` and `npm test`, then check the page with `npm run dev:mock`.
